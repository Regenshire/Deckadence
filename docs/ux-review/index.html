October 10, 2026 · Final review · 6 PM Pacific

Prioritize reliable actions and room for the content.

The existing dark visual language, shared Print / Export dialog, settings categories, and reusable card components are a sound foundation. The biggest release risks are broken pack viewing, keyboard access, and uncertainty around saving. The largest everyday usability improvement is reducing the controls shown before the user reaches their cards.

Try the proposed controls Home & set editor

Review scope

All 44 Jinja templates were parsed; all top-level page templates were inventoried. Core pages were inspected in a browser using the real Flask app and a private snapshot of the local database. Deck management was additionally measured at 390 × 844. This is an expert review, not a user study or an accessibility certification.

The review server isolates runtime files under Export/ux-review/runtime, blocks HTTP mutations, and disables outbound Python requests. Missing cached artwork in this sandbox is not counted as an application defect. External imports, physical printing, full game completion, and every mobile/modal combination remain outside the verified scope. Production files and the user's existing backup edits have not been modified by this review.

Priority in this review: P0 = repair before release because the affected page cannot render; P1 = major access or everyday usability weakness; P2 = refinement to consistency and task flow. These labels describe review recommendations, not confirmed application-wide failures.

P0 · RELEASE BLOCKER

Standalone pack viewing cannot render.

chaos_pack_view.html:94 contains an unmatched endif. Jinja rejects the template before rendering any pack. app.py:36016 uses it for /chaos-draft/view when an opened pack exists. The newer in-page pack viewer uses a separate JSON route; this does not establish that every pack-view entry point is broken.

Fix: use one optional badge container for both foil and special badges. A minimal repair is prepared. The complete corrected template now renders in the isolated server for all four combinations: no badges, foil only, special badges only, and both. Production remains unchanged.

Review the exact patch · Template validation and route inventory · Twelve passing fixture checks

Release check: parse all templates in CI, then render this view with no badges, foil only, special badges only, and both.

P1 · SHARED KEYBOARD BEHAVIOR

Dialogs do not consistently own keyboard focus.

Opening Print / Export from the Deck Builder leaves focus on the page's original button, outside the visible dialog. The shared confirmation in static/js/app.js:881–942 focuses its affirmative action, handles Escape, but does not implement focus containment or restore the opener. The same focus-on-opener behavior was reproduced in Deck Stats, Choose Card Back, and the shared QR overlay. The Add Cards overlay's outer window also lacks dialog semantics. In the populated Momir result fixture, Enter opens image zoom but focus remains on the background image and the overlay has no dialog role.

Improve: one dialog lifecycle for all overlays: capture opener, move focus inside, isolate the background, contain Tab, close the topmost dialog on Escape, restore focus. For destructive confirmations, focus Cancel initially and name both the action and affected objects. Preserve typed confirmation for operations that already require it.

Apply to: Print / Export, card search, alternate art, card backs, print/cutting template selectors, stats, QR, imports, deck deletion, and campaign/pack confirmations. Existing nested dialogs and ongoing jobs need explicit close policies.

Try dialog behavior or select sample decks to try the destructive confirmation. The prototype uses native <dialog>; production can retain existing markup behind the same interface when nesting or compatibility requires it.

P1 · SAVE CONFIDENCE

Users need to know what is saved, and what will be saved.

Settings has a top-level Save All button, plus section buttons labeled Save Settings that submit the entire configForm (static/js/config.js:474–497). Sets and custom-set details also depend on explicit saving, without a shared changed-state indicator. Meanwhile some editor actions persist immediately. Similar-looking controls therefore have different save rules.

Improve: add a reusable dirty-form controller with a small sticky bar only while changes exist. Label the actual scope: “Save all changes” for the current whole-form endpoint. Mark immediately persisted controls as such where ambiguity exists. Keep pending edits after an error; update the saved baseline only after a successful response. A navigation warning should appear only for real unsaved edits. Keep the save bar outside collapsible details so pending changes stay visible, and reveal collapsed sections when a field fails validation.

Apply to: Settings, set selection, custom-set details, pack layouts, campaign/player edits, and the deck metadata fields that still require saving. Do not add dirty tracking to already-persisted card operations.

Try dirty state, discard, save failure, and retry. A production adapter must handle repeated field names, files, disabled controls, and existing asynchronous saves.

P1 · MOBILE TASK ACCESS

Toolbars push the actual collection out of view.

At 390 × 844, the Decks filter form is approximately 376 px high; the results summary starts at y≈711 and the empty selection toolbar at y≈761 with another 159 px of height. The first deck is below the initial viewport. At desktop width, Add Cards shows roughly a dozen filter/sort fields before any results.

Improve: keep Search and the main action visible. Put secondary filters in a single disclosure, with a visible active-filter count and removable summary. Put page-size choices beside pagination. Reveal bulk-action controls only after selection; keep selection scope explicit (“this page” or “all matching”). Clear or reconcile selection when results change.

Apply to: Decks, campaign lists, pack management/history, custom-set card lists, Add Cards, and Deck Roulette. Retain useful existing collapsed filters in the Deck Builder instead of replacing them.

Try the shared collection pattern. The demonstration has local sample data; retain server-side filtering and pagination for real card collections. Do not load all cards into JavaScript.

P1 · CONTROL NAMES

Some repeated controls lose their meaning without visual context.

Browser inspection exposed unnamed campaign/player selectors, unnamed pack-selection checkboxes, unnamed layout dropdowns, and the Momir Select result type dropdown. In the layout editor, desktop CSS hides the span that supplies the wrapped label, so the browser exposes bare comboboxes. Momir's mana field is unnamed and read-only, while its script responds to on-screen keypad clicks rather than typed digits.

Improve: use shared field, icon-button, and row-selection macros. Provide stable id/for associations and contextual names such as “Slot 4 rarity” and “Select [pack name] [tracking code]”. Visually hidden labels must remain in the accessibility tree. Give the mana field a real label and support ordinary keyboard input alongside the touch keypad. Try the labeled keyboard-and-touch input demonstration.

Apply to: all templates and dynamically generated rows. Audit the rendered DOM after opening dialogs, not just source markup. Preserve at least the demonstrated 44 px touch targets; keep visible focus styles across input types.

P2 · TASK HIERARCHY

Management forms compete with the things users manage.

Custom-set details, special categories, and pack types precede the card list. Player import and creation precede the player list. Campaign rows are always in edit mode with several actions, and Delete remains visually prominent on repeated rows.

Improve: show the collection first, one clear primary action, and compact context. Place metadata in “Set details” or “Edit” disclosures; put infrequent actions in a labeled More menu. Keep Add Cards, Open, and Print / Export easy to reach. Avoid forcing a new wizard onto experienced users.

Apply to: custom sets, campaigns, players, decks, and packs using shared page-header and row-action components. This changes information order, not the underlying endpoints or data model.

Try the cards-first set editor, with reusable save and dialog behavior.

P2 · FEEDBACK & RECOVERY

Feedback alternates between alerts, toasts, and local panels.

Several scripts call browser alerts, including deck-save fallback, Chaos Draft errors, Momir validation, and copy/export errors. The shared toast disappears after about 2.8 seconds by default. Some pages expose long-running jobs with different feedback controls.

Improve: use quiet status text for routine saves, field-level errors for invalid input, and persistent actionable messages for failures. Extend the existing FileExportController rather than building a second production job framework. Keep progress factual: indeterminate until real progress exists, and say “download started” rather than claiming the browser saved a file.

Apply to: saves, search/import, PDF/ZIP exports, database refresh, upscaling, and copying decklists. A dismissed job dialog must not imply cancellation; expose Stop only if the backend can actually cancel.

Try output success and failure states. The prototype does not generate a PDF or claim to download one.

P2 · ORIENTATION

Primary destinations and return paths could be clearer.

Home promotes four activities but offers no direct saved-deck shortcut. The large branded introduction and long descriptions delay those activities. Direct entry into a nested editor gives its generic Back control a fallback to Home, even when the logical parent is Sets or Packs. Cards leads directly to Sets although the menu also contains Decks and Packs.

Improve: keep the visual identity, shorten activity copy to a sentence, expose “My decks,” and add compact parent breadcrumbs to nested pages. Extend the existing UINavigation context with explicit parent URLs; keep browser Back separate when history-based behavior is useful. Add aria-current="page" where the navigation already marks an active destination.

Apply to: shared navigation, custom set → pack layout, campaign → packs → pack/history, and deck lists → editor.

Explore the shorter home proposal.

P2 · PRINT EXPECTATIONS

Show the effective output before starting a large export.

The shared Print / Export modal already hides advanced settings well. Its initial view could be more useful with card count, sideboard inclusion, paper/layout, and backs. Pre-print Chaos Draft includes a permanently disabled Print button even though Generate Packs retrieves a PDF. The browser-print return button calls history.back() directly, unlike the safer automatic return function in the same template. On iPhone Safari the script skips automatic printing but the template provides no visible Print button; a lookup for printNowButton has no matching element. This is source-confirmed; a real iPhone print test remains pending.

Improve: add a concise summary computed from the actual print configuration and selected cards. Rename pre-print's main action “Create draft PDF”; remove the inactive duplicate action. Give browser print a visible Print again control and the existing safe return fallback. Use “Print / Export” for card output and “Export backup” for portable data archives where both appear.

Apply to: decks, sets, packs, batch generation, and Momir output. Reuse the print configuration resolver so the summary cannot disagree with the generated file. The demo's sheet count is deliberately fixed sample math, not a replacement for that resolver.

Exact search and replacement for the template blocker

In templates/chaos_pack_view.html, find this complete block, including its indentation:

                {% if card.sheet_is_foil %}
                <div class="chaos-pack-view-badges">
                    <span class="chaos-pack-view-badge">Foil</span>
                </div>
                {% endif %}
                    {% for badge in card.special_badges %}
                    <span class="chaos-pack-view-badge">{{ badge }}</span>
                    {% endfor %}
                </div>
                {% endif %}

Replace it with:

                {% if card.sheet_is_foil or card.special_badges %}
                <div class="chaos-pack-view-badges">
                    {% if card.sheet_is_foil %}
                    <span class="chaos-pack-view-badge">Foil</span>
                    {% endif %}
                    {% for badge in card.special_badges %}
                    <span class="chaos-pack-view-badge">{{ badge }}</span>
                    {% endfor %}
                </div>
                {% endif %}

Prototype boundary: patterns.js demonstrates the interfaces with sample data and simulated persistence. It is not a production drop-in. Do not include the whole file in base.html: extract the controllers into the shared layer, inject real route adapters, and initialize only the component present on each page. Keep the existing app color tokens and scope adopted CSS to component classes.
